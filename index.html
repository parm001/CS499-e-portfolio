Professional Self-Assessment

Professional introduction

My Computer Science program and capstone ePortfolio have prepared me to contribute as an entry-level software developer with a strong interest in secure application development, code quality, and software verification. The program taught me to connect technical decisions to the people and goals they serve. I now approach a computing problem by clarifying requirements, selecting an appropriate design, considering data and algorithm trade-offs, anticipating misuse, verifying behavior, and communicating the result in a form that another person can evaluate and maintain.

The ePortfolio makes that growth measurable. Across the featured enhancements, I produced a warning-clean C++17 redesign with 13 passing checks, a reusable algorithms library with 19 passing checks and two large-input performance comparisons, and a Python/SQLite findings tracker with six automated database tests. These results show more than completed code. They demonstrate a repeatable professional workflow: analyze an existing system, identify risks and constraints, justify a design, implement the change, test normal and adverse cases, incorporate feedback, and present evidence.

My professional values are reliability, security, clarity, and continuous improvement. I want to build software that behaves predictably, protects data, and can be understood by the next developer. The capstone strengthened those values because every improvement had to be supported by a reason, a test, and clear documentation. My immediate goal is a role in software development, application security, or software quality assurance where I can contribute C++, Python, SQL, testing, and secure coding skills while continuing to grow through code review and team delivery.

Program experience and transferable strengths

Collaborating in a team environment

The program showed me that collaboration is a technical practice, not only a meeting activity. In CS 250 coursework, I practiced translating product-owner priorities into user stories, acceptance criteria, sprint work, and reviewable increments. That process required listening for the actual user need, breaking large requests into achievable work, and keeping the definition of done visible. It also reinforced the value of retrospectives: feedback is most useful when it changes the next iteration rather than becoming a note that is never applied.

The capstone implementation was primarily individual, so I do not present it as evidence of a large team project. Instead, it demonstrates habits that make team work more effective: small modules with clear responsibilities, reproducible build instructions, separate test suites, meaningful names, versionable text artifacts, and documented trade-offs. The instructor feedback on the algorithms enhancement is a concrete example. I separated the reusable implementation from the demonstration and verification programs, then added a larger performance comparison. The revision made the code easier for another developer to reuse and made the benefit easier for a nontechnical reviewer to understand.

Communicating with stakeholders

Throughout the program, I learned to adapt communication to purpose and audience. A developer needs interfaces, complexity, failure cases, and commands that reproduce results. An instructor or security reviewer needs traceable evidence. A manager needs impact, priority, and risk stated in plain language. Coursework in secure coding and security policy required translating technical weaknesses into controls and recommendations, while presentations and written reports required organizing those ideas into a decision-ready form.

This portfolio applies that lesson through a short code-review video, concise READMEs, inline narratives, source comparisons, test records, performance evidence, and a database report grouped by risk. The same findings can therefore be examined at different levels of detail. That flexibility supports stakeholder decisions without hiding the technical basis for the recommendation.

Data structures and algorithms

My algorithms and data-structures coursework developed my ability to evaluate a solution rather than stopping when it produces the expected output. In CS 260, I worked with structures such as vectors, linked structures, hash tables, and trees and considered how searching, sorting, insertion, deletion, and traversal behave as input grows. That foundation helps me ask whether a container matches the access pattern, whether an iterator remains valid after mutation, and whether a simpler mathematical or library-supported algorithm is available.

I also learned that complexity and security are connected. Endless recursion, uncontrolled traversal, integer overflow, and invalid indexing are correctness defects that can become denial-of-service or memory-safety risks. My work now combines asymptotic analysis with boundary testing and explicit failure behavior. This approach is visible in the capstone, but it was shaped by earlier coursework that required comparing alternative structures and explaining the cost of each choice.

Software engineering and databases

Software-engineering coursework strengthened my ability to move from requirements to maintainable components. I practiced responsibility separation, interface design, object-oriented organization, version control, documentation, and verification. In CS 320, requirements-based testing reinforced the need to test normal, boundary, and invalid inputs rather than treating successful compilation as proof of correctness. That lesson directly informs how I build verification evidence today.

Database coursework in DAD 220 and CS 340 developed my understanding of relational models, CRUD operations, keys, relationships, integrity rules, and query-driven reporting. I learned to place essential validity rules near the data instead of relying only on interface code. I also learned to treat schema design as a trade-off: normalization improves consistency and reuse, while unnecessary tables and joins can make a small solution harder to maintain. The capstone database artifact applies that foundation through three related tables, constraints, indexes, an audit trigger, parameterized operations, and repeatable reports.

Security mindset

Security became a central professional strength through CS 405 and CS 410. Static analysis, secure coding standards, policy work, and low-level examination taught me to look beyond visible functionality. I learned to question memory lifetime, exception guarantees, input boundaries, integer behavior, data access, trust assumptions, and the ways an attacker could turn a reliability defect into an exploit or service disruption. Reverse-engineering exercises also strengthened my ability to trace control flow and explain behavior that is not obvious from a high-level interface.

My current security process uses defense in depth. Compiler warnings, sanitizers, explicit contracts, bounds checks, database constraints, foreign keys, bound parameters, allow-lists, and adverse-input tests address different failure modes. No single tool proves a system secure, so I combine automated evidence with manual reasoning and clear remediation notes. This mindset prepares me to contribute to development teams that need security integrated into ordinary design and testing rather than added only at release time.

How the artifacts fit together

The portfolio uses one original C++ static-analysis exercise as a consistent baseline and then examines it through three complementary computer science categories. Keeping the baseline constant makes the growth visible: the first enhancement improves architecture and contracts, the second improves algorithms and data structures, and the third turns review findings into trustworthy and reportable data. Together, the artifacts show that I can work across code, performance, verification, persistence, security, and communication.

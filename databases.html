Artifact Narrative

Artifact description

The artifact began as QuestionableCode.cpp, a C++ source file used in CS 405 and CS 410 coursework to compare compiler diagnostics, Cppcheck results, and manual security review. The original intentionally contains unsafe patterns including endless recursion, an out-of-bounds write, iterator invalidation, a dangling pointer, and an exception thrown from a noexcept function. I created the database enhancement in August 2026. It is a Python command-line application backed by SQLite that stores eight findings from the review, validates them through a relational schema, and produces repeatable summaries for decision making. The original C++ file remains unchanged so the relationship between source defects and the enhanced database solution is clear.

Justification and improvements

I selected this artifact because it connects secure software development with dependable data management. The original exercise showed how analysis tools expose defects, but its results were unstructured and difficult to compare, update, or reuse. The database makes those observations durable. A developer, reviewer, or manager can see how many findings are critical, which tool identified each issue, which items remain open, and what remediation was recommended without rereading the source or separate notes.

The central improvement is a normalized three-table schema. scans records the reviewed artifact and context; findings stores each issue and links it to a scan; and finding_status_history preserves workflow changes. Primary keys provide stable identities. NOT NULL, CHECK, UNIQUE, and positive-value constraints reject incomplete or invalid records. Foreign-key enforcement and cascading cleanup protect referential integrity. Indexes support common filters by scan, risk, severity, and status. A trigger records status changes automatically, providing an auditable history without relying on every caller to remember a second insert.

The application layer demonstrates secure database access. Values are passed through bound parameters instead of concatenated into SQL. The only dynamic SQL element—a requested reporting column—is mapped through a fixed allow-list. Transaction contexts keep related operations atomic, and foreign keys are enabled for every connection. Aggregate queries summarize findings by risk, severity, status, and source tool; a priority query isolates high and critical items; and JSON export supports future integrations. Six automated tests verify totals, invalid-value rejection, foreign keys, parameterized handling of injection-like text, audit-history creation, priority reporting, and export behavior.

Reflection and feedback

The enhancement taught me that database reliability begins with the schema, not only with application validation. Checking severity in Python gives clear feedback, but a CHECK constraint remains effective if another script writes directly to the database. The same principle applies to foreign keys and audit history: locating essential rules close to the data creates a second line of defense. I also learned that parameterization and allow-listing solve different problems. Bound parameters protect values, while identifiers such as column names require a trusted mapping because they cannot be bound in the same way.

The main design challenge was choosing enough structure to demonstrate database skills without overengineering a small educational dataset. A larger enterprise model could separate tools, levels, users, and artifacts into more lookup tables, but that would add joins and maintenance without improving this fixed use case. I kept controlled values as schema constraints and separated only entities with distinct lifecycles: scans, findings, and status changes. Grouped totals and a focused priority list also helped translate stored records into decisions for audiences beyond database developers.

I incorporated earlier instructor feedback that my database plan was only a starting concept and did not yet prove database skills. In response, I built the working SQLite schema and Python application, added repeatable seeding and reports, included sample output, and created six automated tests that intentionally try invalid relationships and SQL-like payloads. This changed the portfolio evidence from a description of intended work into an executable, verifiable database solution.

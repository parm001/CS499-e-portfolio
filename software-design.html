Artifact Narrative

Artifact description

The artifact selected for this enhancement is QuestionableCode.cpp, a C++ static-analysis exercise created during earlier CS 405 and CS 410 coursework before the CS 499 capstone. The original file intentionally contains unsafe or unreliable examples used to compare compiler warnings with static-analysis findings. These examples include endless recursion, incomplete copy behavior, an exception thrown from a noexcept function, a pointer to a local variable, an out-of-bounds array write, iterator invalidation, assignment inside an assertion, and broken token traversal. In July 2026, I transformed the artifact into SecureCodeReviewEnhanced.cpp. The original remains unchanged for comparison, while the enhanced version presents the remediations as a cohesive, warning-clean, testable C++17 program.

Justification for inclusion

I selected this artifact because it demonstrates more than the ability to write a new program. It shows that I can evaluate existing code, explain why a design is unsafe, and improve it without losing its educational purpose. These skills matter in professional software development because developers frequently maintain, review, and modernize code written by other people. The side-by-side files let a reviewer trace each risk to a design decision and to evidence that the corrected behavior works.

The enhancement reorganizes unrelated risky examples into focused classes and functions with clear responsibilities and explicit contracts. TypeRegistry performs direct set membership rather than calling itself recursively. CopyableValue uses complete compiler-generated copy behavior. SafeOperation reports status without violating a noexcept contract. safe_local_value returns std::optional<int> rather than exposing a dangling pointer. set_array_value validates an index before updating a vector, and remove_value uses the erase-remove pattern rather than continuing with an invalid iterator.

The revised program also uses const-correct methods, [[nodiscard]] annotations, meaningful names, and targeted comments. I replaced assertion-dependent demonstrations with a reusable VerificationSuite because ordinary assertions can be removed from release builds. The completed program performs 13 runtime checks, compiles with warnings treated as errors, and passes AddressSanitizer and UndefinedBehaviorSanitizer. These components showcase interface design, separation of responsibilities, defensive programming, modern C++ use, testability, and secure software engineering.

Reflection and feedback

The most important lesson from this enhancement was that correcting a defect is not the same as improving software design. A small change can stop one failure, but a stronger enhancement changes the contract, naming, responsibility boundaries, and verification strategy so that the same problem is less likely to return. For example, changing one array index would only hide the immediate boundary error. Accepting a vector by reference, checking the requested position, and returning a success value creates a reusable contract whose failure behavior can be tested.

One challenge was preserving the connection between the original example and each remediation. A broad rewrite could have made the improvement harder to evaluate. I kept each correction focused, named it according to its responsibility, and paired it with targeted checks. A second challenge was deciding how to verify the work without repeating the original assertion mistake. The verification suite reports visible pass-or-fail results in debug and release builds and returns a nonzero exit status when a check fails. Running compiler diagnostics and sanitizers reinforced the value of using several forms of evidence rather than assuming successful compilation proves safety.

I incorporated feedback that portfolio evidence should show working results rather than only describe future plans. The final package therefore includes the original and enhanced files, reproducible build commands, recorded output, 13 runtime checks, a warnings-as-errors build, and sanitizer results. Feedback also identified that my early database concept needed a complete implementation; I addressed that separately in the database enhancement so this artifact could remain focused on software design and engineering.

Course outcome alignment

This enhancement most strongly meets Course Outcomes 2, 4, and 5. The narrative, README, source comments, and verification output communicate the design to an instructor, developer, or employer. C++17, standard-library containers, explicit interfaces, compiler diagnostics, and sanitizers demonstrate professional computing techniques. The redesign anticipates how unsafe recursion, invalid memory lifetimes, boundary errors, iterator misuse, assertion behavior, exception contracts, and null traversal can create failures or vulnerabilities.

The artifact partially meets Outcomes 1 and 3. Its clear interfaces and reviewable evidence support collaborative technical decisions, although the capstone work was completed individually. Direct lookup, bounds checking, vector removal, range calculation, and traversal demonstrate algorithmic thinking, but the separate algorithms enhancement provides the full complexity analysis and trade-off evaluation. The software-design artifact was improved from a set of questionable snippets into a maintainable, executable, and independently verifiable remediation program.
